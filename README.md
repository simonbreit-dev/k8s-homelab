# Disposable Kubernetes Lab on Hetzner Cloud

A personal learning cluster with one control plane and one or more workers.
Terraform provisions Hetzner Cloud infrastructure and bootstraps Tailscale;
Ansible installs containerd, initializes Kubernetes with kubeadm, joins workers,
and installs Cilium. SSH and local API access use Tailscale; cluster traffic uses
the Hetzner private network.

## Structure

- `terraform/`: HCP backend, shared network/firewall/SSH key, node module, and generated Ansible inventory.
- `terraform/modules/node/`: one server, private address, and cloud-init bootstrap.
- `ansible/playbooks/site.yml`: node preparation, private-network checks, cluster bootstrap, and readiness checks.
- `ansible/roles/`: common packages, containerd, Kubernetes prerequisites, control plane, workers, and Cilium.
- `ansible/inventory/group_vars/all.yml`: shared Kubernetes networking, versions, and local kubeconfig path.

`ansible/inventory/hosts.yml` is generated by Terraform and ignored by Git. Do not
edit it manually; the first node is the control plane and the remaining nodes are
workers.

## Prerequisites

- Terraform 1.16.4 and an HCP Terraform organization/workspace.
- A Hetzner Cloud project/API token and an OpenSSH public key with its matching private key.
- Tailscale on the local machine, MagicDNS, and a policy allowing SSH and Kubernetes API access to `tag:k8s-node`.
- A Tailscale OAuth client with the `auth_keys` scope and permission to assign that tag.
- Python, Ansible Core, `kubectl`, and Helm on the Ansible controller.

Ansible Core 2.21.4 was used for local review checks. Install the controller
requirements and pinned collections:

```shell
cd ansible
python3 -m venv .venv
source .venv/bin/activate
python -m pip install ansible-core -r requirements.txt
ansible-galaxy collection install -r requirements.yml
```

The Python requirements belong in the environment running Ansible, including
`netaddr` for the `ansible.utils.ipaddr` filter. The playbook installs
`python3-debian` on nodes for APT repository management.

## Terraform configuration

Authenticate and select the HCP workspace from the repository root:

```shell
terraform -chdir=terraform login
export TF_CLOUD_ORGANIZATION="your-organization"
export TF_WORKSPACE="your-workspace"
```

Use HCP workspace **Local execution mode** for the current inventory workflow.
State remains in HCP, but Terraform creates the inventory on your machine. With
remote execution, `local_file` writes on the disposable HCP runner, and the local
Ansible inventory is not created. A portable remote-execution handoff is not
implemented.

For local execution, export these provider credentials or load them through the
committed `.envrc` and an ignored `.env.local` using `direnv allow`:

```dotenv
HCLOUD_TOKEN=replace-me
TAILSCALE_OAUTH_CLIENT_ID=replace-me
TAILSCALE_OAUTH_CLIENT_SECRET=replace-me
TF_CLOUD_ORGANIZATION=your-organization
TF_WORKSPACE=your-workspace
```

Copy `terraform/config.auto.tfvars.example` to
`terraform/config.auto.tfvars` and replace `ssh_public_key`. Keep credentials out
of tfvars. Local tfvars and environment files are excluded from HCP configuration
uploads by `terraform/.terraformignore`; remote runs require inputs and provider
credentials configured in the workspace.

Defaults are three `cx23` nodes running `ubuntu-24.04` in `nbg1`, named
`k8s-lab-node-1` onward, with public IPv4/IPv6 and the tag `tag:k8s-node`.
`node_count` supports 2–10 nodes; `control_plane_count` must be 1. The public
firewall allows Tailscale UDP traffic and blocks other ingress. Private node IPs
start at `10.0.1.11` in `10.0.1.0/24`.

The OS image name is resolved to an image ID during planning; a newer image can
replace nodes. Changes to cloud-init data, including automatically recreated
Tailscale auth keys, also trigger server replacement. Ansible currently requires
Ubuntu/Debian-style packages and an IPv4 default route. Public IPv4 is always
enabled; arbitrary image overrides are not supported by the complete bootstrap
workflow.

## Provision and configure

From the repository root:

```shell
terraform -chdir=terraform init
terraform -chdir=terraform fmt -check -recursive
terraform -chdir=terraform validate
terraform -chdir=terraform plan
terraform -chdir=terraform apply
```

Terraform finishes before cloud-init and Tailscale registration necessarily do.
Wait for every generated hostname to resolve and become reachable through
Tailscale. If bootstrap fails, use the Hetzner console to inspect
`cloud-init status --wait` and `journalctl -u cloud-final -u tailscaled`.

Run Ansible from its directory so it loads `ansible.cfg`:

```shell
cd ansible
source .venv/bin/activate
ansible-playbook --syntax-check playbooks/site.yml
ansible-playbook playbooks/site.yml
```

Use the full inventory for bootstrap. The plays share node facts and worker
inspection results; targeted `--limit` runs and full `--check` execution are not
currently supported. File-existence guards avoid repeating `kubeadm init` and
`join`; this is a bootstrap workflow, not cluster recovery or an upgrade tool.
Kubernetes packages install the available patch of the configured minor and are
then held; changing `kubernetes_repo_version` does not upgrade existing nodes.

Ansible fetches an admin kubeconfig and changes its API endpoint to the control
plane's Tailscale hostname:

```shell
kubectl --kubeconfig="$HOME/.kube/k8s-lab-admin.conf" get nodes -o wide
```

Cilium installation waits for its Helm release, Ready nodes, and CoreDNS.

## Cleanup and limitations

Run `terraform -chdir=terraform destroy` from the repository root. Before server
deletion, a best-effort SSH call runs `tailscale logout`; failure does not block
destroy. Tailscale registration is a cloud-init side effect, so check the admin
console for stale devices afterward. Terraform manages reusable, preauthorized,
ephemeral auth keys; secret values are stored in Terraform state.

The lab intentionally uses one control plane, root SSH, disabled Ansible SSH
host-key checks, fixed private-network ranges, and manual operations. Tailscale
and containerd installations are not pinned to exact versions. The fetched
kubeconfig is also retained locally after destroy. No automated CI/CD is included.
